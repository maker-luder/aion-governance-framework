# SLSA / SBOM / artifact-attestation implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **This document is a plan, not permission to execute it. Human review of this exact plan and a selected execution method precede Task 1.**

**Goal:** Prepare an independently verifiable source-snapshot SBOM and attestation evidence chain without reopening public releases, granting normal PR CI signing authority, or inferring a SLSA level.

**Architecture:** A reviewed artifact-definition record specifies one engineering candidate, a deterministic source snapshot tarball. A read-only build job creates and validates that candidate plus its SPDX 2.3 SBOM; a separate, event-restricted job may attest only the exact transferred bytes after a distinct Human workflow-permission decision; an independent read-only verifier binds both predicates, signer identity and exact source/digest to a release-evidence record. The record remains `HOLD` until a separate Human release decision. No task changes the frozen historical manifests or existing Quality/CodeQL permissions.

**Tech Stack:** Python 3.11+, GitHub Actions, GitHub CLI `gh attestation verify`, `actions/attest` pinned to `1e69f48acb82d1966a394da916b4c1698aa569d6` (v4.2.2 at 2026-09-25), Syft CLI v1.52.0 Linux amd64 release archive SHA-256 `caeedb81fb0491615f1ebd1761e4145d41ee86dd2cc7bf80669f9f5ad9d6133d`, SPDX 2.3 JSON, pytest, JSON Schema.

**Spec:** `docs/superpowers/specs/2026-09-25-slsa-sbom-attestation-design.md` at design commit `892f0d11c86f157f95667e8799199b817454acb9`.

## Current technical decisions and evidence

1. **Candidate subject, not a release authorization:** one `aion-source-snapshot-<40-hex-source-sha>.tar`, generated by `git archive --format=tar --prefix=aion-<40-hex-source-sha>/ <exact-source-sha>` from an immutable commit. Type `source-archive`, output count `1`, SHA-256 of raw tar bytes, `source_head` exactly that commit, `repository=maker-luder/aion-governance-framework`. A gate record must explicitly name this shape and be Human-reviewed before it is called an **official** release artifact. Until then it is a local engineering specimen; `OFFICIAL_RELEASE_ARTIFACT=UNSPECIFIED -> DO_NOT_ATTEST` remains true. The historical ZIP shape is not reused as authority.
2. **Syft CLI rather than `anchore/sbom-action`:** the standalone release binary performs local scanning only; it has no action defaults for `upload-artifact`, `upload-release-assets` or `dependency-snapshot`. Download only `syft_1.52.0_linux_amd64.tar.gz` from the versioned Anchore release URL and verify the pinned SHA-256 before extraction/execution. No install script, floating tag, dependency submission, or release-asset upload. Scan the extracted archive filesystem with `syft dir:<extracted-root> -o spdx-json@2.3=<sbom-path>`; do not assume Syft directly scanning a generic tar has complete coverage. Assert a nonempty package/file inventory appropriate to the chosen source and reject scan errors. The exact executable version is checked with `syft version`.
3. **SPDX 2.3 JSON:** SPDX's current family is 3.0, but Syft documents `spdx-json` as 2.3 and current GitHub SBOM verification documents `https://spdx.dev/Document/v2.3`. Freeze the initial interoperable path to `SPDX-2.3` and that predicate type; validate with the official SPDX 2.3 JSON schema at immutable spec commit `aadf3b0b8dbbabdb4d880b0fc714255fea436ff7`, path `schemas/spdx-schema.json`, using the repository CI pin `jsonschema==4.26.0`. The SPDX document namespace must be a valid unique URI, not a hard-coded arbitrary namespace. Do not claim conformance merely from JSON parsing. Revalidate tool output and GitHub predicate support at the Phase 1/2 execution date; a changed result stops the phase for plan revision instead of silently substituting 3.0.
4. **Attestation:** a future dedicated workflow may use only `actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6`, first without `sbom-path` for `https://slsa.dev/provenance/v1`, then with the same `subject-path` and validated `sbom-path` for `https://spdx.dev/Document/v2.3`. `actions/attest` writes attestations by design; no `packages: write`, `contents: write`, `artifact-metadata: write`, `push-to-registry`, or release upload. Its privileged job has `contents: read`, `id-token: write`, `attestations: write` and does not checkout or execute transferred artifact content.
5. **Verifier:** `gh attestation verify <subject.tar> -R maker-luder/aion-governance-framework --signer-workflow maker-luder/aion-governance-framework/.github/workflows/supply-chain-attest.yml --source-digest <40-hex-source-sha> --source-ref refs/heads/main --predicate-type <expected> --format json`, once per predicate, plus independent JSON checks for the exact subject SHA-256, predicate type, source/run/workflow identity and nonempty verified result. The installed `gh` version and behavior are recorded in evidence; if the current CLI rejects these options, hold for a reviewed pin/plan update. A JSON file's presence alone never passes verification.

Primary current docs: [GitHub attestation generation](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [GitHub CLI verification](https://cli.github.com/manual/gh_attestation_verify), [Syft output formats](https://github.com/anchore/syft/wiki/output-formats), [Syft v1.52.0](https://github.com/anchore/syft/releases/tag/v1.52.0), [SPDX specifications](https://spdx.dev/use/specifications/), [SLSA v1.2](https://slsa.dev/spec/v1.2/). GitHub release/tag API read-back supplied the Syft archive digest and `actions/attest` commit above; both are re-read at implementation time.

## Review Focus

1. A `workflow_dispatch` started on a non-`main` ref or supplied a different `source_sha`: reject before privileged job or artifact transfer (Task 3 test).
2. A syntactically valid SPDX document that names the wrong artifact or has an empty inventory: fail structural validation (Task 2 test).
3. A valid signed attestation for the correct digest but unexpected repository/workflow identity or predicate: reject, not merely warn (Task 4 test).
4. A correct artifact transferred across jobs but mutated before signing: recompute SHA-256 in privileged job and reject (Task 3 test).
5. All technical gates pass while release authority is absent/stale: evidence record stays `HOLD` and no tag/release/deployment mutation is possible (Task 5 test).
